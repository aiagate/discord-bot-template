# 目的から分解した実装改善計画

I1〜I5を実装した。具体的な契約は[実現方法](architecture.md)、検証結果は
[受入条件](acceptance.md)を参照する。

## 目的

自ら判断し行動するAI集団が、マスターを継続して支援し、具体的な成果につなげる。
各キャラクターが経験と作業を継続し、必要に応じて協力できるようにする。
マスターが一手ごとに指示したり、同じ事情を説明したりする負担を減らす。

実装は、判断材料の受け渡しと作業の所有関係を管理し、担当者の判断を保存・実行へ反映する。
何が役立つか、再調査や発言が必要かは、記憶と文脈を踏まえて担当者が判断する。

## ハイレベルユースケース

[既存のH1〜H6](purpose.md)を維持し、今回の改善との対応を示す。
ここには製品・保存形式・配置などの手段を含めない。

| ID | できること | 改善項目 |
| --- | --- | --- |
| H1 | 状況や関心の変化から、役立つ支援の機会に気づく | I3・I4 |
| H2 | 必要な支援を自ら判断・実行し、成果につなげる | I1・I4 |
| H3 | 途中の支援を忘れず、状況に応じて続け、待ち、見直し、終える | I1・I3 |
| H4 | 仲間が個性と異なる見解を活かし、協力して支援する | I1・I2 |
| H5 | 過去の交流と経験を活かし、理解と判断を更新する | I2・I3 |
| H6 | マスターと対話し、考え・状況・成果を伝え、意思の変化を活動に反映する | I2・I4・I5 |

## ユースケースと実装改善

### I1 キャラクターごとの作業環境で着手・継続・引継ぎする

対応: U3・U4・U5。

**契機 → 行動 → 結果:** 作業開始・再開・引継ぎの際、担当者が自分の作業環境で
対象と前回の変更を確認し、他の担当者の作業を混ぜずに続きを進められる。

- 実装: `work/<char_id>/`をCodexの起動場所とし、書込み範囲も担当者の領域に合わせる。
  初期化時に作業ルートの`AGENTS.md`を作り、記憶・リポジトリ・作業資料の利用方法を案内する。
  既存ファイルは再初期化や再起動で上書きしない。
  対象リポジトリはghqで管理し、キャラクター別の作業ツリーを持つ。
  引継ぎには対象リポジトリ、変更の所在、根拠、未完了事項を渡す。
  受け手は自分の作業環境を使い、送り手の個人領域を引き継がない。
- 無いと困ること: 活動の担当変更で同じ作業場所を共有し、個人の作業や変更が混ざる。
  作業環境の案内がなければ、各領域の用途や参照先を毎回探し直すことになる。
- 受入条件: 同じ対象を担当するAとBで、作業場所と未コミット変更が分かれる。
  AからBへの引継ぎ後も成果への参照が残り、Bの実行場所はBの領域になる。
  作業ルートの案内が初期化で作られ、編集内容は再起動後も保持される。
  検証用の案内に固有の文字列を置き、実際のCodexのセッション記録で、
  起動時に読み込まれた指示にその本文が含まれることを確認する。

```text
work/
└── <char_id>/                 # Codexの起動場所
    ├── AGENTS.md             # 作業環境の案内と参照先
    ├── memory/               # 個人の記憶
    ├── repos/
    │   └── github.com/<owner>/<repo>/
    └── tasks/<activity_id>/   # 必要な場合の資料・成果物
```

共通のマスター方針、基盤のDB、実行履歴の正本は個人領域の外に置く。
活動は担当が変わっても同じIDと履歴を維持する。配置変更で作業権限は拡張しない。

作業ルートの`AGENTS.md`には次を短く記載する。

- キャラクター定義とマスター方針の参照先。
- `memory/`の探し方と、必要な根拠へ戻る方法。
- `repos/`の配置と、対象リポジトリに適用される`AGENTS.md`等を作業前に確認する手順。
- `tasks/`の用途と、今回の活動状態・引継ぎ情報の参照方法。

進捗や未回答の質問はI3、接続状況はI4から渡す。案内に現在の状態や記憶本文を複製しない。
基盤の出力契約・停止処理・権限制御を、案内の記述で置き換えない。
作業アダプタが起動場所などの読み込み条件を整え、Codexでは標準の読み込みを使う。
別のモデルへ交換する場合は同じ案内を入力に含め、標準で読む場合の重複添付を避ける。

Codexは起動時にプロジェクトルートから起動ディレクトリまでの案内を読み込む。
配下のリポジトリの案内まで一括で読み込まれるとは扱わず、対象の作業前に確認する。
配下の案内の確認は担当者の行動であり、この項目の基盤による読み込み保証には含めない。
読み込み範囲と上書きファイルの扱いは[公式仕様](https://learn.chatgpt.com/docs/agent-configuration/agents-md)に従う。

### I2 同じキャラクターの会話と作業で個人記憶を利用する

対応: U5・U6・U8。

**契機 → 行動 → 結果:** 会話・作業・経験の保存時、担当者が自分の記憶と必要な根拠を
参照・更新し、その後の会話と作業でも同じ記憶を利用できる。

- 実装: 記憶の保存先を`work/<char_id>/memory/`にする。
  更新は実行した担当者に紐付け、引継ぎ先の記憶へ誤って保存しない。
  会話には基盤が読み出した記憶を、作業には同じ保存先を参照できる形で渡す。
  共通の事実・実行履歴と個人の解釈を分け、
  記憶から根拠への参照を保つ。他者の記憶を自分の記憶として自動複製しない。
- 無いと困ること: 他者の記憶を上書きしたり、会話と作業で異なる個人記憶を参照したりする。
- 受入条件: Aの記憶更新が、次のAの会話入力と作業側の参照先の両方へ反映される。
  AとBが同じ記憶キーを使っても衝突しない。AからBへの引継ぎを含む結果でも、
  Aの記憶更新はAに保存される。会話モデルを交換しても記憶の所有者と参照先は変わらない。

### I3 再実行時に継続に必要な状態を受け取る

対応: U2・U4・U6。

**契機 → 行動 → 結果:** 再実行・再起動の際、担当者が前回の判断、伝えた内容、
残っている質問と待機理由を確認し、その状態から次の判断を始められる。

- 実装: 最新の判断、直近の送信済みの内容、未回答の質問、現在の待機理由を、
  件数制限のある実行ログとは別の状態として入力する。
  未送信・送信済みを区別し、原記録への参照を保持する。
- 無いと困ること: コマンド記録の増加によって、継続に必要な情報が入力から押し出される。
- 受入条件: 多数の操作記録が追加されても必要な状態が入力に残り、再起動後も復元される。
  未送信の文章を送信済みとして渡さない。

### I4 実行基盤の観測結果を使って状況を確認する

対応: U2・U3・U7。

**契機 → 行動 → 結果:** 認証・接続・配信などの状況を確認する際、担当者が基盤の
観測結果を受け取り、自分の実行環境から見える範囲と区別して扱える。

- 実装: 基盤が持つ設定の有無、接続・配信の直近の結果、実際に適用した作業範囲を渡す。
  観測結果には時刻と出典を付け、成功・失敗・未観測を区別する。
  認証値そのものは渡さず、過去の成功を現在の接続保証にはしない。
- 無いと困ること: 分離された環境に設定が見えないことを、サービス全体の設定不足と取り違える。
- 受入条件: Codex側に認証環境がなくても基盤の観測結果を受け取れる。
  未観測を成功や設定不足に変換せず、秘密値が入力に含まれない。

### I5 作業を保存し、発言要求のある内容を表現・配信する

対応: U3・U7・U8。

**契機 → 行動 → 結果:** 作業結果や返答内容が決まった際、担当者が結果を記録し、
伝える必要があれば発言を要求する。発言しない結果も残り、要求した内容が配信へ進む。

- 実装: 毎回の実行記録と任意の発言要求を分け、既定の`notify=True`を廃止する。
  マスターに伝える結果・理由・根拠・未確認事項・質問を、要約だけに削らず表現担当へ渡す。
  返答待ちの質問と完了には発言要求を必須とする。基盤の停止・失敗通知も維持する。
  通常の会話の返答は作業成果の有無に依存させない。
- 無いと困ること: 記録の保存が自動的に発言へ結びつき、表現担当には説明に必要な情報が届かない。
- 受入条件: 発言要求のない結果は保存され、配信されない。要求した伝達項目は表現担当の入力に残る。
  質問・完了を発言要求なしで受理しない。基盤の停止・失敗通知と通常会話の返答を失わない。
  表現失敗時の代替文でも伝達内容を保持し、配信再試行で作業を再実行しない。

## 実装と判断の境界

| 項目 | 実装が担うこと | 記憶・文脈を使って担当者が判断すること |
| --- | --- | --- |
| I1 | 作業場所を分け、引継ぎ情報を渡す | 何に取り組み、誰に何を引き継ぐか |
| I2 | 記憶の所有者と保存・参照先を揃える | 何を経験として残し、いつ参照するか |
| I3 | 保存済みの判断・質問・配信状態を入力に残す | 同じ調査を続ける価値や、新しい支援の機会 |
| I4 | 観測結果と未観測の区別を受け渡す | 得られた事実の意味と次の一手 |
| I5 | 発言要求と伝達内容を保存・受け渡し・配信する | 今伝える必要があるか、何を勧めるか |

I1〜I5の保存・受け渡し・配信はモデルを置き換えたテストで確認する。
I1の案内の読み込みは、実際のCodex起動でも確認する。
意味の重複、支援の有用性、説明の分かりやすさは別途実モデルで評価する。
直近の送信内容を入力に残すI3と、発言要求のある結果を配信するI5は、判断を支える仕組み。
モデルが同じ発言を毎回要求する問題まで、この実装で解消したとは扱わない。

## 実施範囲と順序

I1・I2で所有者と保存先を揃え、I3・I4で判断に渡す状態を整え、I5で表現・配信への
受け渡しを改める。会話・作業・表現の責務分離と、思考モデルを交換できる契約を維持する。
新しい発言がなくても時刻や観測を契機に再開できる既存の自律実行も維持する。

継続方針と個別の仕事を分ける状態管理の拡張は後順位とする。
通知の価値を採点する仕組み、意味の重複を審査する専用モデル、
待ち時間の推定、並列実行の追加は今回の改善に含めない。
