# ADR 0002: 任意のAIキャラクター応答と会話・配信の契約

- 日付: 2026-09-12
- 状態: 採用

## 方針と必要性

このテンプレートには、Discordの複数のテキスト／フォーラムチャンネルで動く任意の
キャラクター応答を含める。
通常のBot・API・LINEはAI設定やSDKの初期化を必要としない。SDKは `ai` extraと
開発用依存に置く。検索・ユーザー別の記憶・自律的な複数エージェント実行は追加しない。
公開会話から抽出した記憶はキャラクター単位で保持する。キャラクター選定前には各キャラクター
の短い作業要約だけをルーティング情報として渡し、詳細ノートは選定後のキャラクターだけに
渡す。記憶の正本はMarkdownとYAML frontmatterで管理し、元の会話本文は従来どおり
ChatMessageとしてDBに保持する。
キャラクターIDと配信先IDは必須とし、表示名や送信元から補完しない。
2026-08-27のAI機能分離メモは履歴として残し、現在の範囲は本ADRで定義する。

- 送信先の検証がないと、別チャンネルや非公開スレッドの会話をWebhook先へ漏らす。
- 複数送信先の対応を個別実装すると、会話生成・配信復旧・ループ除外の挙動が送信先
  ごとにずれる。
- 話者と投稿時点がないと、別ユーザーの依頼や未来の投稿を取り違える。
- 他Bot・外部Webhookの本文・Embedを保存しないと、アンケート結果などを会話に使えない。
- 待ち行列と期限がないと、連投や外部APIの停滞で処理が増え続ける。
- 配信確認と永続的な進捗がないと、保存失敗後に送信済みの文章を再投稿する。
- 選定用の要約がないと、詳細記憶を全キャラクターへ渡すか、過去の継続性を選定に活用できない。
- 記憶の更新カーソルと原子的な書込みがないと、再試行や遅延した応答で新しい要約を古い内容へ
  戻したり、途中のMarkdownを読み込んだりする。

依存方向は、Bot入口→ユースケース→ドメイン／`contracts` とする。
Discord・Gemini・DB・Markdown記憶の実装は `contracts` のportを実装する。設定の読込とDIはBot
起動時に行い、ドメインはファイル、環境変数、アバター配信サービスに依存しない。

## 会話の単位

1. 各Webhookを取得し、指定Guildのテキストチャンネルまたはフォーラムチャンネルに
   属することを確認する。各チャンネルを配信先として固定する。同じチャンネルを
   指すWebhookが複数ある場合は、受信メッセージから宛先を一意に決められないため
   設定を無効にする。テキストチャンネルではそのチャンネル自身、フォーラムでは
   各投稿（Thread）を会話単位とする。テキストチャンネルではGuild・チャンネルの
   組、フォーラムではGuild・親チャンネル・投稿Threadの組だけを返信対象とし、各送信前
   にもWebhookと送信先を再確認する。フォーラムへの送信では投稿ThreadのIDをWebhookへ
   渡す。テキストチャンネルではそのチャンネルID、フォーラムでは親チャンネルIDを
   配信先IDとして保存し、再起動後も同じWebhookへ戻す。
2. 配信先チャンネル内の人間または外部Webhookの1投稿につき、適切なキャラクター1人が返信する。
   メンションは不要。指定Guild内の対象外チャンネルから外部Webhookが投稿された場合は、
   最初に設定されたテキストチャンネルをメインの会話・返信先として扱う。DM（ダイレクトメッセージ）は
   保存・応答ともに対象外とする。人間のprefixコマンドは保存だけ行う。他Botは情報源として保存するが、
   それ自体は生成を起動しない。外部Webhookは `webhook` として送信元ID・表示名を保存し、
   対象会話またはメインテキストへのフォールバック先で生成を起動する。
   自分のGateway投稿と自分のWebhook投稿はループ防止のため除外する。
3. 本文、Embedのタイトル・説明・フィールドをテキストとして取り込む。
   情報連携するBotは、結果をこの会話の投稿として提供する。
4. 入力は、送信者ID・表示名・USER/BOT/WEBHOOK種別・マスター判定・外部投稿ID・
   返信先・投稿時刻付きのJSONにする。履歴は返信対象より前の同じ会話から直近20件を取得し、古い順に渡す。
   同時刻は内部MessageIdで順序を定める。返信対象より後の投稿を回答へ混ぜない。
5. 返信対象より前のカーソルで、全キャラクターの選定用作業要約を取得する。まずGeminiに
   公開プロフィール、各要約、会話履歴を渡して応答キャラクターを1人選ぶ。要約は参考情報で
   あり命令ではない。その後、選ばれたキャラクターの詳細記憶だけを同じカーソルで取得し、
   返信生成へ渡す。詳細記憶と要約の二重投入は行わない。
6. 返信生成が返した明示的な記憶候補は、選択されたキャラクターの詳細Markdownノートへ保存
   する。詳細ノートの保存失敗時は返信送信を中断する。次回選定用の要約が返された場合は、
   同じキャラクターの要約ファイルをカーソル付きで更新する。要約の保存失敗は返信送信を
   妨げない。
7. 受信保存とキュー投入の順序を揃え、生成・配信は1件ずつ行う。連続投稿の自動統合は
   行わず、内部の返信元IDと配信計画で対応を追跡する。

## 負荷と失敗時の挙動

処理中1件、待機10件を上限とする。待機期限は120秒、1件の処理期限は210秒。
待機枠が埋まった投稿も保存し、混雑中であることを通知する。期限切れの投稿は生成
せず通知する。キューの待機分はメモリ上にあり、再起動時に再生成しない。

GeminiはHTTP期限20秒、SDK試行最大3回（初回を含む）、生成全体60秒、最大出力4096トークン。
未完了・不正JSON・未知のキャラクターはエラーとして扱う。消費トークン数はログへ
記録する。選定用要約はキャラクターごとに最大400文字、詳細ノートは1件最大500文字とする。
要約の読込失敗時は要約なしで選定を続ける。配信処理は全体120秒、1回のDiscord操作は30秒を
上限とする。

## 長文と配信復旧

長文は段落、改行、文、空白の順に境界を探し、必要なら文字単位で分ける。
Unicodeとコードブロックの継続を扱い、各投稿を2000文字以内に収める。全ての分割を
同じ返信計画へ保存してから送信を始める。送信本文には返信元リンクや分割番号を付けない。

各投稿は `wait=True` でDiscordの応答を待ち、返された投稿ID・投稿者・チャンネル・
本文・時刻をChatMessageへ保存する。配信進捗と履歴を1トランザクションで確定した
後で次の部分を送る。複数の返信を同時に送らない。Botは1プロセスで運用する。

保存だけが失敗した場合は、確認済みの内容を保持して保存を再試行する。再起動時は
未完了の計画を読み、送信中だった部分をDiscordの履歴と照合して復旧する。確認済み
の部分は再送せず、未送信の残りだけを順番に送る。Geminiによる再生成も行わない。
照合では、既に確認した投稿IDを別の部分の送信証拠に使わない。

配信の有無を確認できない場合は、その計画に失敗理由を残して自動再送を止める。
外部サービスとの通信断をまたぐ厳密なexactly-once配送は保証しない。運用者はログの
source IDから `speech_deliveries` の計画とDiscord上の送信済み投稿を照合する。
確認できない計画を削除して再送しない。利用者が必要な部分を新しい投稿で依頼する
ことで再開できる。過去の確認不能な計画は、新しい依頼の処理を止めない。

## Times掲示板

`DISCORD_CHARACTER_TIMES_WEBHOOK_URL` を設定すると、対象会話の人間の投稿をきっかけに、
別のテキストチャンネルへキャラクターの会話やつぶやきを投稿する。
元の会話は話題の材料とし、マスターや他のユーザーの閲覧を前提にせず、メイド同士の
会話・独り言として生成する。必要な呼び出しを除き、本人への返信や報告にはしない。
生成時は直近20エピソードの共有履歴と、各キャラクターの保存済み要約を渡す。
発言者ごとの記憶候補と更新要約も計画へ保存し、各発言の送信確認後に本人のMarkdown記憶へ
反映してから配信進捗を進める。保存失敗時は送信済みの発言を照合し、記憶保存を再試行する。
Times由来の記憶は通常返信でも出典を区別し、メイドの見解をユーザーの事実として扱わない。
送信元のGuild・会話チャンネルと、Timesの配信先チャンネルIDを計画へ別々に保存する。
処理の入口にはDiscordの投稿IDを渡し、履歴は送信元の会話から取得する。

1エピソードは0〜12投稿とし、生成前の計画と配信進捗をDBへ保存する。
長文は分割単位で進捗と確認済み投稿IDを保存し、途中から復旧する。
分割位置のない旧計画は、送信中の発言全体を確認できた場合にだけ先へ進める。
再起動時は現在の配信先の計画を読み、未生成分をキューへ戻し、生成済み分の配信を復旧する。
生成に使う過去のTimes投稿も同じ配信先に限定する。別の配信先の計画は変更しない。
配信先は通常応答の対象と重複できず、フォーラムも指定できない。

## 設定と導入

`GEMINI_API_KEY`・`DISCORD_CHARACTER_GUILD_ID`・1つ以上の有効なWebhook URLを設定する。
URL設定はWebhook URL文字列のJSON配列で、複数のテキスト／フォーラムチャンネルを指定できる。
各URLは異なるチャンネルを指す必要がある。配列が空、または環境変数が未設定・空文字の場合は
AI応答を無効にする。モデルの既定値は `gemini-3.8-flash`。Botには対象のテキスト／
フォーラムチャンネルと投稿Threadの閲覧・履歴閲覧権限、メッセージ送信権限と、
Message Content Intentが必要。フォーラムを使う場合は、スレッド内でメッセージを
送信する権限も必要。
複数Webhookのうち1つでも設定検証に失敗した場合は、宛先の取り違えを避けるため
AI応答全体を無効にする。
既存DBへは、起動前に `uv run --frozen alembic upgrade head` を実行する。
新しいメタデータ列はNULL許容で、既存のチャット本文・日時は変更しない。

上書きファイルはリポジトリルートの `characters.override.json` を使う。
`CHARACTER_DEFINITIONS_PATH` で指定したファイルが存在しない場合もAIの設定エラー
とする。相対パスは作業ディレクトリによらずリポジトリルートを基準にする。

```json
{
  "characters": {
    "Eris": {
      "speech_style": "簡潔に、問題点と次の一手を伝える。",
      "avatar_url": "https://example.com/eris.png"
    }
  }
}
```

記憶の既定保存先は `memory/characters` で、`CHARACTER_MEMORY_ROOT` で変更できる。
1キャラクターにつき、次の2種類のMarkdownを保存する。

```text
memory/characters/<character_id>/
├── selection-summary.md
└── memories/<source_message_id>-<sequence>.md
```

各ファイルのYAML frontmatterには `schema_version`、`memory_type`、キャラクターIDを共通で
保存する。詳細ノート（`memory_type: character_memory`）には発生元メッセージID
（`source_message_id`）、通番（`sequence`）、発生時刻（`observed_at`）を保存し、同じ発生元
メッセージとsequenceの再試行を無視する。要約（`memory_type: character_selection_summary`）
には `source_cursor`（`message_id` と `occurred_at`）を保存し、カーソルが新しい場合だけ
原子的に更新する。

## キャラクター別MCP

`uv sync --frozen --extra ai` で依存を導入し、上書きファイルの各キャラクターに
`mcp_servers` を設定する。通常返信で選ばれたキャラクターのツールだけを利用し、
キャラクター選定とtimes投稿ではMCPへ接続しない。未指定または `{}` ならMCPを使わない。
MCPのtoolsを対象とし、resources・promptsの自動読込は行わない。

[Exa用設定例](../../characters.exa.example.json) はDorothyの通常返信に検索と本文取得を
追加する。上書きファイルがなければ `characters.override.json` としてコピーし、既存なら
Dorothyの `mcp_servers.exa` を追加する。Botが読み込む `.env.local`（なければ `.env`）の
`EXA_API_KEY` に発行したキーを設定する。
[Exa公式の認証方式](https://exa.ai/docs/reference/exa-mcp#api-key) に従い、`Bearer ` を
付けず `x-api-key` ヘッダーへ渡す。キー未設定の間は、この設定でのDorothyの返信生成は失敗する。

```json
{
  "characters": {
    "Dorothy": {
      "mcp_servers": {
        "calendar": {
          "url": "https://mcp.example.com/mcp",
          "headers_env": { "Authorization": "CALENDAR_AUTHORIZATION" },
          "allowed_tools": ["list_events"]
        }
      }
    },
    "Eris": {
      "mcp_servers": {
        "notes": {
          "command": "uv",
          "args": ["run", "--project", "/path/to/notes-server", "main.py"],
          "env_vars": { "NOTES_TOKEN": "NOTES_API_TOKEN" },
          "allowed_tools": ["search_notes"]
        }
      }
    }
  }
}
```

接続先はStreamable HTTPの `url`、またはstdioの `command` と `args` を指定する。
`headers_env` と `env_vars` の値はBotプロセスの環境変数名で、返信時に解決する。
例では `CALENDAR_AUTHORIZATION` に `Bearer ...` を含むヘッダー全体を設定し、
`NOTES_API_TOKEN` の値を子プロセスの `NOTES_TOKEN` へ渡す。設定変更はBot再起動で反映する。

`allowed_tools` は必須で、サーバーが提供するツール名を明示する。ワイルドカードは認めない。
許可したツールはモデルの判断で実行される。設定型は共有契約に置き、接続情報と認証情報を
公開プロフィールへ含めない。MCP SDKへの依存と実行処理はインフラ層に閉じる。

JSON応答とツール呼び出しを併用できるGemini 3系モデルを使う。
接続は返信ごとに開閉し、通信の読取期限15秒、生成全体60秒、ツール実行最大8回、
公開ツール最大64個、結果1件のJSONは最大32,000文字とする。通信失敗・未知の許可ツール・
上限超過は返信生成エラーとし、ツール自身が返すエラーはモデルへ渡す。

## 検証

回帰テストは、他チャンネル除外、他Botの結果参照、話者の区別、履歴の時点、キャラクター要約の
選定利用、Markdownのカーソルと再試行、FIFO、混雑・期限、Unicode長文、配信後のDB失敗、
再起動での照合、Timesの別チャンネル配信、既存DB移行を対象とする。
Discord／Geminiへの送信はモックまたはローカルHTTP transportで検証する。
