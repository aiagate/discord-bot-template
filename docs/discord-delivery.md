# キャラクターの発言をWebhookへ統一する

## 目的とユースケース

H4・H6を実現するため、マスターが誰の発言かを識別でき、会話・成果・操作への応答を
同じ窓口で受け取れるようにする。ハイレベルユースケースの定義は変更しない。

- U7: 伝える内容と話者を保存し、その話者の名前・アバターで配信する。
- U7: 停止・再開・状態確認を受け付け、実際の受付結果を同じ配信経路へ残す。
- U8: 通常の返答も同じ経路で届け、送信した発言を新しい依頼として取り込まない。

## 必要性

- 名前とアバターを投稿者に反映しないと、複数人の発言が一つのBotの発言に見える。
- 全送信の経路を揃えないと、操作への応答だけ別の話者・別の再送処理になる。
- 宛先を検証・固定しないと、設定変更で未送信の内容が別の場所へ流れる。
- 送信前の試行と確認結果を保存しないと、中断後に送信済みの発言を繰り返す。

## 実装契約

Botは耳、Webhookは口とする。Botは入力受付・接続観測・配信確認のための履歴読取りを
担う。通常の返答、自律報告、質問、完了、失敗、操作への応答をWebhookから送る。
Botからの`send`・`reply`による代替送信は設けない。

依存は入口 → ユースケース → 契約。Webhook Publisherは既存のPublisher契約を実装し、
SDK・Webhook URL・送信先検証は外部アダプタで扱う。思考・表現担当に送信権限を渡さない。

- 一データディレクトリにつき一つの窓口・Webhookを使う。全キャラクターで共有し、
  `Character.name`と任意の`avatar_url`を投稿ごとに指定する。未指定のアバターはWebhookの既定値。
- `DISCORD_WEBHOOK_URL`と`--channel-id`を使い、起動時と送信前に所属サーバーと宛先を確認する。
  スレッドの場合は親チャンネルのWebhookを使い、送信にはスレッドIDを指定する。
  サーバー・チャンネル・WebhookのIDをDBに固定し、別の組合せでの起動を拒否する。
  URLは保存せず、基盤の観測には設定の有無と検証結果だけを渡す。
- Botのログインと宛先検証が済んでから受信・自律実行・配信を開始する。
- `!stop`・`!resume`・`!status`は入力IDで重複を防ぎ、受付結果と応答を一括保存する。
  操作時の担当者を話者とし、確定した定型文をLLMに渡さず配信する。停止は配信成功を待たず反映する。
- 発言の識別子は`Notice.id`。自律発言に人間の投稿IDを要求しない。
  送信前に試行時刻を保存し、`wait=True`で取得したメッセージID・宛先・送信者・本文・時刻を残す。
  再試行では保存済みの確認結果を使う。送信後に中断した場合はWebhook IDと通知マーカーで履歴を照合する。
- 確認できない試行は自動再送せず保持する。明確なリクエスト拒否は修正後に再試行できる。
  `pending`で未配信の通知と試行・確認結果を参照できる。
  一つの未確認通知で他の通知や作業を止めない。外部配信の厳密な一回実行は保証しない。
- 長文は本文の冒頭と全文添付で届け、メンションは無効にする。
  送信失敗でも保存済みの文面を維持し、作業や表現生成をやり直さない。

元実装の複数宛先Routerや長文の分割送信は、現在の一窓口構成には追加しない。
通常の作業・記憶・会話と配信の独立性は維持する。

## 受入条件

- 二人のキャラクターが同じWebhookから、それぞれの名前・アバターで発言する。
- 会話、自律報告、操作応答のいずれでもBotの送信APIを使わない。
- 停止の重複入力やプロセス再起動で、操作・応答が重複しない。
- 宛先変更、異なる親のスレッド、Webhook不備では送信を開始しない。秘密値をログやモデル入力に出さない。
- 送信直後の終了・保存失敗から再開しても、履歴から確認できる発言を再送しない。
- 確認不能な送信、明確な拒否、長文、メンション、ファイルの解放を検証する。
- 自分のWebhook投稿は新しい会話や作業を起動しない。
