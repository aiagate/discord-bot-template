# 実現方法

[ユースケース](use-cases.md)を実現するための選択を記す。
製品を交換しても[ハイレベルユースケース](purpose.md)は変えない。

## 責務と依存方向

- 会話の思考担当: 発言の理解、返答内容、作業への依頼・訂正・停止・再開の意図。
- 行動担当（初期実装はCodex）: 状況理解、記憶探索、次の一手、作業、引継ぎ、達成判断。
- 表現担当（初期実装はGemini）: 発言意図と確認結果を、本人として読みやすい文章にする。
- 実行基盤: 起動、待機、再開、予算、状態保存、配信、停止。
- モデル外の記録: 支援方針、キャラクター、根拠、記憶、実行状態の正本。

依存は入口 → ユースケース → 契約。外部アダプタも同じ契約に依存する。
共有メッセージは`contracts/messages`、外部境界は`contracts/ports`に置く。
ユースケースはDiscord、Codex、Geminiをimportしない。

## 必要性

- 支援活動を保存しないと、人間の発言がない間に目的を失う。
- 時刻による起動がないと、待機した作業を自分で再開できない。
- 結果と根拠がないと、質問待ちや失敗を達成と取り違える。
- 一つの状態更新主体がないと、担当の重複と記憶更新の食い違いが起こる。
- 表現を分けないと、口調の調整が作業の開始や完了を左右する。
- 会話の処理が独立していないと、挨拶でも進行中の作業が中断される。
- 思考の契約を製品から分けないと、提供元の変更が対話の挙動や記憶の構造に波及する。

初期版は一台・一人のマスター・順次実行。分散キュー、プラグイン基盤、ベクトル検索、
汎用組織モデルは持たない。実例から不足を確認して追加する。

## 実装との対応

| UC | 実装 |
| --- | --- |
| U1 | `LocalStore.create`、`collective add` |
| U2・U3 | `SupportRunner.tick`、`CodexThinker.run` |
| U4 | `LocalStore.claim/recover/fail`、`Outcome`の明示的な判断 |
| U5 | `handoff`による担当変更、次回実行への同じ活動と根拠の引継ぎ |
| U6 | `LocalStore.context/project`、Markdownの探索と出典付き記憶 |
| U7 | `LocalStore.inform/control`、`Communicator`、ローカル・Discord配信 |
| U8 | `ConversationRunner`、`ConversationThinker`、`LocalStore.receive/finish_conversation` |

SQLiteの一トランザクションで活動の更新、判断、記憶更新案、報告内容を保存する。
Markdownへの反映は保存後に行い、失敗した反映だけを再試行する。
同じデータディレクトリの実行主体をファイルロックで一つに制限する。
入力や停止で活動の版を進め、古い版に対する判断は履歴だけに残す。
会話・作業・配信はそれぞれ独立したループで動く。

## 状態と起動

### 作業・記憶・伝達の契約

[改善計画](improvements.md)のI1〜I5を次の境界で実装する。

- `Activity.repositories`に依頼対象の取得元を保存する。作業アダプタがghqで担当者の
  `work/<char_id>/repos/`へ取得する。既存の作業ツリーを自動更新せず、引継ぎ先にも
  独立した作業ツリーを用意する。変更の所在と根拠は同じ活動の判断記録から引き継ぐ。
- 起動場所は`work/<char_id>/`。初期化時に`AGENTS.md`と`memory/`、`repos/`を作り、
  既存の案内を上書きしない。実行ごとの状況は`tasks/<activity_id>/context.json`へ保存する。
- 記憶の投影先は判断記録の実行者で決める。会話には本人の記憶本文、作業には同じ保存先を渡す。
- `Continuity`は最新の判断、送信済みの発言、未回答の質問を持つ。
  活動の状態・次の一手と合わせて、直近の操作ログとは別に毎回渡す。
- `RuntimeObservation`は基盤の観測元・時刻・成否と、設定の有無だけを保存する。
  接続、表現、配信、会話の結果を記録し、未観測は未知のまま渡す。認証値を渡さない。
- `Outcome.communication`は任意の発言要求。内容・伝える理由・根拠・未確認事項・質問を持つ。
  質問と完了には要求を必須とし、質問は`next_step`と一致させる。
  内部の判断要約と理由は、発言要求がなければ作業記録にだけ残る。
- `Notice`は発言要求と配信ID・話者・表現済み文章を保存する。
  表現担当には発言要求全体を渡す。表現失敗時は全項目を含む文章を基盤が組み立てる。

共有型は契約に、保存・ファイル配置・SDKの処理は外部アダプタに置く。
ユースケースは契約だけに依存し、記憶の意味や通知の価値を判定する機構は追加しない。

Codexは担当者の領域を`workspace-write`の起点にする。追加の書込み先と共通の`/tmp`を
許可せず、一時ファイルとキャッシュも本人の領域へ向ける。読取りの隔離は行わない。
ルートの`AGENTS.md`はCodexの標準機能で読み込む。配下の対象リポジトリの案内は
編集前に担当者が確認する。案内の編集はsandboxや基盤の状態遷移を変更しない。

支援活動には目的、達成条件、担当、状態、次回起動時刻、未完了事項を持たせる。
一回のモデル呼出し終了と、支援活動の達成を区別する。
構造化出力で担当者の判断を受け取り、基盤が活動の状態を更新する。
完了時には全達成条件の番号と根拠を必須にする。
根拠の意味と達成の判断は担当者が行う。基盤の形式検証だけで作業の正しさを保証しない。
担当者は起動時に、支援方針に含まれる資料や作業場所を自ら調べ、前回からの変化を確認する。
新しい観測情報が届いた場合も、時刻を待たずに再判断する。外部サービスの常時監視は初期版の対象外。

| 判断 | 活動の扱い |
| --- | --- |
| 続ける | 未完了事項と次の一手を保存し、再び実行する |
| 時間を置いて確認する | 再確認する理由と時刻を保存する |
| 返答を待つ | 確認事項を残し、追加情報まで実行しない |
| 達成した | 達成条件に対応する根拠を保存する |
| 仲間に引き継ぐ | 指定した仲間へ目的・根拠・未完了事項を渡し、次の実行を始める |

マスターの停止指示と実行予算の上限は、担当者の判断によらず基盤が反映する。

途中で落ちた場合は結果不明の試行として記録し、次回は実際の状態を確認する。
外部操作の厳密な一回実行は保証しない。再開時に無条件で同じ操作を繰り返さない。

## 記憶と根拠

Markdownを通常のファイル操作で探索し、短い案内から必要な原資料へ進める。
根拠と判断記録は追記し、解釈としての記憶は出典を添えて更新する。
記憶更新案の確定と実行状態の更新は基盤が扱う。モデルにDBを直接書かせない。
個人記憶は`work/<char_id>/memory/`、共有の原記録は`evidence/`に置く。
記憶更新案には判断の実行者を使い、引継ぎ後の担当者と取り違えない。
モデル固有の会話セッションは継続の補助であり、長期記憶の正本にしない。
初期版では各回を新しいCodex threadで開始し、モデル外の記録から状況を復元する。
直近30件の記録と、件数制限から独立した`Continuity`を入力する。
それ以前の原記録は`evidence/`で探索できる。
質問は作業への追加情報を受け付けた時点で未回答から外す。挨拶だけでは外さない。
コマンド等の観測記録は一件24000文字まで保存する。内面推論は記録しない。

## コミュニケーション

DiscordではBotを受信、Webhookを全発言の送信に使う。キャラクター別の名前とアバター、
操作への応答、宛先と送信確認の契約は[Webhook配信設計](discord-delivery.md)に定義する。

原文は会話の未処理入力として保存し、通常の発言では活動の版や起動時刻を変えない。
会話担当は`ConversationContext`を受け取り、`ConversationDecision`を返す。
提供元やモデル名は入口で選び、ユースケースと記録には製品固有の形式を持ち込まない。
GeminiとOpenAI APIのアダプタを用意し、どちらも作業ToolやMCPを持たない。
表現担当には確定した発言要求の全項目を渡す。会話担当と行動担当は本人の同じ人格・記憶を参照する。

会話の判断、必要な活動の変更、報告内容、入力の処理済み状態を一括して保存する。
作業に関わる場合は原文を担当者へ渡す。要約を唯一の入力にしない。
後から届いた停止などに追い越された作業依頼は、適用しなかったことを伝えて処理を終える。
その他の活動の版変更では、最新の状態から再判断する。
送信済みの文章は対話履歴として残し、表現の言い換えを作業の達成根拠にはしない。
表現生成や配信の失敗は、作業結果と次回実行の保存を取り消さない。

## 参照した思想と仕様

- [OpenViking: Context Layers](https://docs.openviking.ai/en/concepts/03-context-layers): 概要から必要な詳細を読む。
- [OpenViking: Architecture](https://docs.openviking.ai/en/concepts/01-architecture): 内容と検索索引を分離する。
- [Codex App Server](https://learn.chatgpt.com/docs/app-server): thread、turn、結果通知の境界。
- [Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md): 起動時の案内の読み込み。
- [ghq](https://github.com/x-motemen/ghq/blob/master/README.adoc): 個人ごとの取得先と既存作業の保持。
- [Gemini Function Calling](https://ai.google.dev/gemini-api/docs/function-calling): 表現に専念する経路には作業関数を渡さない。

OpenViking自体は初期依存に含めない。`viking://`は仮想ファイルシステムであり、
このプロジェクトの通常のMarkdown保存と同一実装ではない。
